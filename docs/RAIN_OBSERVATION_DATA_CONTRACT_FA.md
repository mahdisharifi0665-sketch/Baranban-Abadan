# قرارداد داده مشاهده‌ای باران‌بان آبدان — نسخه ۱.۰.۰

## هدف
این قرارداد، داده باران‌سنج را از پیش‌بینی مدل‌ها جدا می‌کند تا در فازهای بعدی امکان ارزیابی مستقل پیش‌بینی فراهم شود. وجود schema و validator به معنی اتصال به ایستگاه واقعی نیست.

## هویت ایستگاه و منبع
هر رکورد باید شناسه پایدار ایستگاه، نام، مختصات WGS84، منطقه زمانی نام‌دار و در صورت دسترسی ارتفاع را داشته باشد. برای ایستگاه‌های خارج آبدان، فاصله تا مختصات مرجع آبدان (28.0794, 51.7694) ثبت می‌شود و داده هرگز به‌عنوان اندازه‌گیری مستقیم آبدان معرفی نمی‌شود.
منبع باید یکی از این انواع باشد: ایستگاه رسمی، باران‌سنج شخصی، API، گزارش دستی یا برآورد شبکه‌ای. نام ارائه‌دهنده، ابزار اندازه‌گیری و ارجاع منبع تا حد امکان ثبت می‌شود. داده شبکه‌ای/ماهواره‌ای مشاهده مستقیم باران‌سنج محسوب نمی‌شود.

## زمان و مقدار
- زمان شروع و پایان بازه مشاهده و زمان دریافت مستقل و اجباری‌اند.
- زمان‌ها باید ISO-8601 دارای Z یا offset باشند؛ timezone ایستگاه جداگانه نگهداری می‌شود.
- بازه به‌صورت نیمه‌باز [start,end) تفسیر می‌شود.
- مقدار بارش بر حسب میلی‌متر است؛ مقدار منفی نامعتبر و مقدار null فقط برای مشاهده مفقود مجاز است.
- نوع اندازه‌گیری باید interval_total یا cumulative_counter باشد. مقدار تجمعی شمارنده نباید با بارش همان بازه اشتباه شود.
- کاهش شمارنده نسبت به رکورد قبلی باید با counter_reset=true علامت‌گذاری و بررسی شود؛ در غیر این صورت پرچم خطا تولید می‌شود.

## کنترل کیفیت
validator موارد زیر را بررسی می‌کند: فیلدهای الزامی، نسخه schema، timestamp و offset، ترتیب بازه، مختصات، مقدار منفی، نوع منبع و وضعیت کیفیت.
ممیزی سری زمانی موارد زیر را گزارش می‌کند: رکورد تکراری برای ایستگاه/بازه، هم‌پوشانی بازه‌ها، شکاف زمانی در صورت تعیین cadence مورد انتظار، و reset اعلام‌نشده شمارنده.
این ابزار داده مشکوک را خودکار اصلاح نمی‌کند و صفر بارش را از داده مفقود استنتاج نمی‌کند. یافته‌ها باید پیش از پذیرش برای اعتبارسنجی مدل بررسی شوند.

## وضعیت کیفیت
raw: دریافت شده ولی هنوز تأیید نشده؛ accepted: پس از QC پذیرفته شده؛ suspect: نیازمند بررسی؛ rejected: رد شده؛ missing: بازه فاقد مقدار (value_mm=null).
پرچم‌ها باید دلیل کیفیت را با شناسه‌های پایدار ثبت کنند.

## نمونه مسیر پردازش
دریافت منبع → حفظ payload/فایل اصلی → تبدیل به رکورد نسخه‌دار → اعتبارسنجی ساختاری → ممیزی سری زمانی → بازبینی انسانی موارد suspect → پذیرش کنترل‌شده → اتصال به آرشیو پیش‌بینی برای backtest بدون نشت اطلاعات.

## محدودیت و ورودی لازم
در حال حاضر منبع مشاهده‌ای واقعی و تأییدشده برای آبدان در مخزن پیکربندی نشده است. برای ادامه ingestion عملیاتی باید یکی از این موارد فراهم شود: خروجی ایستگاه رسمی با مجوز/دسترسی، API معتبر، یا فایل/ثبت منظم باران‌سنج شخصی با زمان و مقدار مشخص. تا آن زمان fixtureهای تست صرفاً داده مصنوعی QA هستند و نباید به‌عنوان بارش واقعی استفاده شوند.
