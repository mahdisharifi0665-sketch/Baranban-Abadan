# ارزیابی اولیه منابع داده — باران‌بان آبدان ۵.۱

تاریخ بررسی: 2026-11-11
وضعیت: آزمون اولیه زنده API برای شش محصول در مختصات آبدان اجرا و ثبت شده است؛ این تست دسترسی و پوشش نمونه را نشان می‌دهد، نه مهارت پیش‌بینی یا تأیید نهایی منبع.
تصمیم: Open-Meteo فعلاً نامزد یکپارچه‌سازی اولیه است، نه منبع نهایی تأییدشده.

## شواهد مستندات

- مستندات Forecast API مدل ECMWF IFS HRES با وضوح اسمی ۹ کیلومتر و افق پیش‌بینی تا ۱۵ روز را فهرست می‌کند؛ در افق‌های بلندتر گام زمانی داده می‌تواند از ساعتی به ۳ و سپس ۶ ساعته تغییر کند. بنابراین «ساعتی» بودن کل ده روز را نباید فرض کرد.
- مستندات Ensemble API مدل‌های ECMWF IFS 0.25°، GFS Ensemble 0.25° و ICON EPS Global را فهرست می‌کند. جدول همان مستندات برای ECMWF IFS Ensemble تا ۱۵ روز، GFS Ensemble 0.25° تا ۱۰ روز، و ICON EPS Global تا حدود ۷٫۵ روز را ذکر می‌کند. پوشش دقیق متغیر بارش و زمان‌بندی برای مختصات آبدان باید با درخواست واقعی آزموده شود.
- API عمومی برای استفاده غیرتجاری بدون کلید API در دسترس معرفی شده؛ استفاده تجاری نیازمند شرایط/دسترسی متفاوت است. مجوز داده ECMWF IFS open data به CC BY 4.0 اشاره دارد؛ این موضوع نباید به معنی یکسان بودن مجوز تمام داده‌های گردآوری‌شده توسط واسطه تلقی شود.
- API عمومی، مدل‌ها را به یک سری زمانی seamless متصل می‌کند؛ این رفتار برای داشبورد عمومی مفید است، اما برای مقایسه مستقل مدل‌ها و بازتولید چرخه‌های تاریخی کافی نیست. باید endpoint/پارامتر مدل مجزا یا آرشیو single-run مناسب استفاده شود.

- احتمال خام ده‌روزه می‌تواند از ECMWF و GFS به‌صورت دو خروجی جداگانه ارائه شود، مشروط به پاسخ واقعی و پوشش اعضای کافی.
- ICON در روزهای پایانی افق ۱۰روزه داده ensemble ندارد؛ نباید روزهای ۸ تا ۱۰ را با extrapolation یا پرکردن از مدل دیگر تکمیل کرد.
- هیچ احتمال تجمیعی چندمدلی تولید نشود تا زمانی که روش کالیبراسیون/ترکیب روی داده تاریخی مستقل طراحی و ارزیابی نشده باشد.
- «وضوح اسمی مدل» با دقت واقعی پیش‌بینی نقطه‌ای آبدان برابر نیست؛ روش انتخاب سلول و اثر ساحلی باید گزارش شود.

## تطبیق متغیرها و زمان‌بندی بر اساس مستندات Ensemble API

- متغیر precipitation در مستندات به‌صورت مجموع بارش یک ساعت قبل تعریف شده است؛ بنابراین برای ساخت ۲۴ ساعت باید ۲۴ بازه ساعتی کامل، بدون شکاف و هم‌پوشانی جمع شوند.
- CAPE در فهرست متغیرهای ensemble دیده می‌شود.
- Vertical Velocity در سطوح فشاری در بخش Pressure Level Variables فهرست شده است؛ قرارداد علامت/واحد باید از metadata منبع دریافت و در adapter تثبیت شود.
- PWAT/Precipitable Water در فهرست متغیرهای صفحه Ensemble API که بررسی شد مشاهده نشد؛ تا وقتی منبعی با نام متغیر، واحد و سطح تعریف‌شده تأیید نشود، PWAT نباید در خروجی به‌عنوان داده موجود نمایش داده شود.
- فهرست متغیرها و دسترسی آن‌ها به مدل انتخابی وابسته است؛ وجود متغیر در صفحه عمومی تضمین نمی‌کند که برای هر مدل/چرخه/نقطه موجود باشد.
- API دارای انتخاب cell_selection است؛ حالت land نزدیک‌ترین سلول مناسب خشکی با توجه به مدل ارتفاعی ۹۰ متری را ترجیح می‌دهد، sea سلول دریایی و nearest نزدیک‌ترین سلول را انتخاب می‌کند. برای آبدان هر سه حالت باید با داده واقعی مقایسه شوند.
- مستندات می‌گویند timezone در Ensemble API ممکن است تغییرات DST داخل بازه را با offset ثابت مدیریت کند؛ در نرم‌افزار باید timestampها با timezone database و مرزهای نیمه‌باز تبدیل شوند، نه با تکیه بر offset ثابت پاسخ API.

## نتیجه عملی برای آبدان

1. Open-Meteo برای نمونه‌سازی و دسترسی ساده به مدل‌های جهانی، نامزد مناسبی است.
2. منبع مستقل/مستقیم NOAA، DWD و ECMWF باید به‌عنوان گزینه پشتیبان و برای راستی‌آزمایی خروجی‌ها بررسی شود.
3. هیچ endpoint تا زمانی که مختصات 28.0794, 51.7694، متغیر precipitation، چرخه و افق آن با پاسخ واقعی بررسی نشده، «تأییدشده» محسوب نمی‌شود.
4. افق ۱۰روزه قطعی و افق ۱۰روزه احتمالاتی دو قابلیت جدا هستند. در روزهای انتهایی که ICON EPS یا GFS ensemble پوشش ندارند، احتمال باید خالی/غیرقابل‌محاسبه بماند؛ پرکردن آن با مدل دیگر بدون روش کالیبره‌شده ممنوع است.
5. به علت احتمال انتخاب سلول ساحلی/دریایی در منطقه آبدان، cell selection و land/sea mask و فاصله سلول باید صریحاً ذخیره و کنترل شود. برای بارش، downscaling آماری دما لزوماً قابل تعمیم نیست.

## گام‌های لازم پیش از تصویب منبع

- اجرای درخواست آزمایشی در مختصات هدف برای ECMWF deterministic، GFS deterministic، ICON deterministic و سه ensemble مربوطه.
- ذخیره پاسخ خام، header/metadata، زمان دریافت و hash؛ کنترل واحد و بازه تجمع بارش.
- بررسی cell selection در حالت land و nearest و مقایسه سلول‌ها و فاصله آن‌ها از مختصات.
- بررسی دسترسی واقعی به CAPE، PWAT (در منبع مستقل)، omega/vertical velocity، رطوبت و باد؛ عدم وجود هر متغیر باید در feature matrix ثبت شود.
- تأیید شناسه دقیق مدل‌های انتخابی API از enum رسمی و اجرای درخواست نمونه؛ نام نمایشی مدل را مستقیماً به شناسه API تبدیل نکنید.
- بررسی نرخ درخواست، timeout، شرایط استفاده، attribution و حقوق ذخیره‌سازی/بازنشر.
- تعیین منبع اصلی و fallback فقط پس از تکمیل ماتریس فوق.

## آزمون پنجره‌های دقیق روز تقویمی آبدان — GitHub Actions run #64

بر اساس تعریف Open-Meteo، مقدار hourly precipitation مجموع یک ساعتِ قبل از timestamp است؛ بنابراین برای جمع روز تقویمی محلی، نمونه‌های ساعت 01:00 تا 00:00 روز بعد لازم‌اند. منبع رسمی: https://open-meteo.com/en/docs/ensemble-api (Hourly Parameter Definition و start_hour/end_hour).

پنجره آزموده‌شده: از `2026-11-12 01:00` تا `2026-11-22 00:00` به وقت Asia/Tehran، دقیقاً 240 نمونه ساعتی که بازه‌های نیمه‌باز 10 روز کامل را پوشش می‌دهند. timestampها یکنواخت، پیوسته، هم‌تراز و منطبق با ابتدا/انتهای درخواست بودند.

این آزمون یک مسئله زمانی مهم را حل کرد: 240 timestamp از 00:00 تا 23:00، به‌تنهایی 24 ساعت کامل از نیمه‌شب تا نیمه‌شب را تشکیل نمی‌دهد؛ برای مقادیر «preceding hour sum»، مرزهای 01:00 تا 00:00 لازم‌اند. Adapter در `src/open-meteo-time-adapter.mjs` این نگاشت را انجام می‌دهد و آزمون آن در `qa/test-open-meteo-time-adapter.mjs` قرار دارد.
