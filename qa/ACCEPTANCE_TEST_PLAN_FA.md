# برنامه تضمین کیفیت و پذیرش — باران‌یار

این سند مکمل مشخصات محصول و فنی باران‌یار (مبنای نسخه ۵.۱) است. هدف، کاهش ریسک و جلوگیری از انتشار نسخه آزمون‌نشده است. «بدون هیچ باگ» تضمین‌پذیر نیست؛ معیار انتشار، عبور مستند از آزمون‌ها و اعلام محدودیت‌های باقی‌مانده است.

## سیاست انتشار
- تا پیش از تکمیل آزمون‌ها، وضعیت پروژه توسعه/آزمایش است؛ نه آماده انتشار.
- تغییرات ابتدا در شاخه کاری انجام شوند؛ پس از بازبینی و موفقیت CI به main ادغام شوند.
- هیچ خطای آزمون با حذف آزمون، نادیده‌گرفتن خطا یا مقدار ثابت ساختگی رفع‌شده تلقی نشود.
- هر باگ باید بازتولیدپذیر، دارای شناسه، شدت، علت ریشه‌ای، اصلاح و آزمون رگرسیون باشد.
- داده هواشناسی، پیش‌بینی و مشاهده واقعی باید جدا و قابل ردیابی باشند.
- هیچ کلید API یا داده محرمانه‌ای در کد یا مخزن عمومی قرار نگیرد.

## مرحله صفر — تثبیت نیازمندی و معماری
- [ ] تأیید نهایی نقطه مرجع مکانی؛ تا آن زمان مختصات کاری در سند موقت است.
- [ ] انتخاب و مستندسازی ارائه‌دهنده/منابع واقعی داده و مجوز استفاده.
- [ ] ثبت محصولات هر مدل، چرخه اجرا، تفکیک مکانی/زمانی، دسترسی ensemble و محدودیت‌ها.
- [ ] بررسی امکان واقعی تحلیل شعاع ۵ کیلومتر و تعریف روش شبکه/نمونه‌برداری بدون ادعای پوشش کاذب.
- [ ] تعریف قرارداد داده (schema)، واحدها، منطقه زمانی و مدیریت مقادیر مفقود.
- [ ] تعیین معماری دریافت داده، ذخیره‌سازی، موتور محاسباتی، رابط کاربری و ثبت رخداد.
- [ ] تعیین رفتار برنامه در قطع اینترنت، خطای API، محدودیت نرخ، پاسخ ناقص و داده منقضی.
- [ ] نگهداری امن کلیدهای API و عدم قرار دادن آن‌ها در مخزن عمومی.

## مرحله یک — آزمون‌های واحد محاسبات
- [ ] آستانه ۵ میلی‌متر: ورودی‌های ۰، ۴٫۹، ۵ و ۵٫۱.
- [ ] آستانه ۱۰ میلی‌متر: ورودی‌های ۹٫۹، ۱۰ و ۱۰٫۱.
- [ ] آستانه ۲۵ میلی‌متر: ورودی‌های ۲۴٫۹، ۲۵ و ۲۵٫۱.
- [ ] جمع روزانه و تجمعی با داده ناقص، تکراری و بازه‌های نامنطبق.
- [ ] پنجره‌های ۲۴ساعته بدون هم‌پوشانی ناخواسته.
- [ ] تبدیل UTC به Asia/Tehran و مرز روز/ماه/سال.
- [ ] گردکردن اعداد و واحد mm؛ تفکیک نرخ بارش از تجمع.
- [ ] احتمال ensemble با اعضای معتبر/نامعتبر؛ مخرج فقط اعضای معتبر.
- [ ] نبود ensemble => عدم تولید احتمال درصدی.
- [ ] آزمون Brier Score و کالیبراسیون با داده آزمایشی شناخته‌شده.
- [ ] جلوگیری از میانگین‌گیری ساده مدل قطعی و ensemble یا پنجره‌های زمانی متفاوت.

## مرحله دو — آزمون یکپارچه‌سازی و تاب‌آوری
- [ ] پاسخ موفق API و تبدیل به schema داخلی.
- [ ] پاسخ خالی، ناقص، خراب، دیررس و دارای واحد/زمان نامعتبر.
- [ ] timeout، قطع اینترنت، خطای سرور، محدودیت نرخ و تلاش مجدد کنترل‌شده.
- [ ] جلوگیری از استفاده از داده قدیمی به‌عنوان داده تازه.
- [ ] ثبت منبع، زمان دریافت، زمان صدور و چرخه مدل در تمام خروجی‌ها.
- [ ] عدم نمایش عدد ساختگی هنگام شکست منبع.
- [ ] بازیابی داده ذخیره‌شده پس از راه‌اندازی مجدد.
- [ ] آزمون امنیت: کلیدها و اطلاعات محرمانه در log یا APK افشا نشوند.

## مرحله سه — آزمون رابط کاربری
- [ ] فارسی و راست‌چین؛ تاریخ و ساعت محلی صحیح.
- [ ] نمایش اولویت‌دار پیش‌بینی ۰ تا ۶ ساعت، سپس ۶ تا ۲۴ ساعت و روند ۷ روز.
- [ ] تفکیک احتمال، مقدار بارش، آستانه و کیفیت داده.
- [ ] نمایش داده ناکافی، کهنه و اختلاف مدل‌ها با زبان ساده.
- [ ] عدم نمایش درجه A تا D به‌عنوان درصد.
- [ ] نمایش زمان آخرین به‌روزرسانی.
- [ ] عملکرد در صفحه کوچک، چرخش صفحه و اندازه متن بزرگ.
- [ ] نمایش خطای قابل فهم به‌جای صفحه خالی یا توقف برنامه.

## مرحله چهار — اعتبارسنجی هواشناسی
- [ ] ذخیره پیش‌بینی‌های صادرشده با نسخه و ورودی‌های دقیق برای جلوگیری از نشت داده آینده.
- [ ] تطبیق با باران‌سنج معتبر آبدان؛ در نبود آن، ایستگاه نزدیک همراه فاصله و محدودیت.
- [ ] ثبت رخدادهای آستانه ۵، ۱۰ و ۲۵ میلی‌متر.
- [ ] ارزیابی خطای مقدار، زمان‌بندی و امتیاز احتمالاتی با تعداد نمونه.
- [ ] تفکیک نتایج بر اساس افق ۰–۶ ساعت، ۶–۲۴ ساعت و روزهای ۱–۷.
- [ ] عدم تنظیم وزن مدل‌ها با رخدادهای مجموعه ارزیابی.
- [ ] ۵ تا ۱۰ رخداد فقط بازبینی اولیه است، نه اثبات مهارت آماری.
- [ ] ثبت محدودیت داده مشاهده‌ای و پرهیز از ادعای دقت اثبات‌نشده.

## مرحله پنج — آزمون انتشار اندروید
- [ ] ساخت reproducible در CI با نسخه‌های مشخص JDK/Gradle/Android SDK.
- [ ] build تمیز از clone تازه مخزن.
- [ ] نصب، اجرا، به‌روزرسانی و حذف روی نسخه‌های هدف Android.
- [ ] مجوزهای حداقلی، شبکه و حالت آفلاین.
- [ ] مصرف باتری، حافظه و پایداری.
- [ ] تولید APK آزمایشی debug؛ انتشار نهایی فقط با امضای امن و تأیید مالک.
- [ ] بررسی وابستگی‌ها، آسیب‌پذیری‌ها و مجوز کتابخانه‌ها.

## معیار اعلام آمادگی
1. همه آزمون‌های بحرانی و اصلی موفق باشند.
2. هیچ باگ بحرانی/شدید باز نمانده باشد.
3. منابع داده و محدودیت‌ها مستند باشند.
4. احتمال‌ها و محاسبات آستانه آزمون شده باشند.
5. گزارش CI و اعتبارسنجی قابل مشاهده و تکرار باشند.
6. موارد غیرقابل‌آزمون به علت نبود داده یا محدودیت بیرونی صریحاً فهرست شوند.

## وضعیت فعلی
این برنامه آزمون هنوز اجرا نشده است. تا زمان وجود کد اجرایی، موتور و گزارش آزمون، هیچ ادعایی درباره عبور از آزمون‌ها یا نبود باگ مطرح نمی‌شود.
